# 05 · 知枝接入、LLM Wiki、AI 复核与安全提交

依赖：01 契约、02 任务/身份、03 模型适配器。04 不是本工作包的强依赖，可先用已有知枝成果闭合第一条链路。

## 一、保留知枝的学习主体

保留 Electron→loopback Starlette→React/Mantine→SQLite 的现有学习体验；只替换统一模式下 Wiki 出口。审计定位：knowledge_learning.py 的首次作答和解析状态；knowledge_material_model.py 的配置 hash 和结构请求；knowledge_wiki.py:107–359 的草稿、托管块、hash 与 fsync+replace；knowledge_first.py 的概念候选；local.py 的 schema v31。具体行号在实施时重核。

建议增加 KnowledgeBackend 接口，LocalVaultBackend 沿用旧本地模式，RemoteKnowledgeBackend 调统一服务。配置显式切换，不能双后端同时写同一成果。统一模式停用原裸写出口，只允许起草和提交；离线暂存为本地 outbox，不偷偷退回另一份正式库。

LearningOutcome 通过 POST /learning/outcomes 输入现有 concept/card/session ID、设备ID、版本、用户原话/实践证据、建议目标 entry_id；返回 change_id/task_id，不直接声称“已写入”。服务按设备+session+outcome_revision 幂等。

“完成学习”“阅读解析”“用户解释”“有实践证据”各自独立。禁止将两题做完标为掌握，禁止 AI 生成答案后登记成用户回答。

## 二、LLM Wiki 增量生成流水线

1. 仅接收已收藏 Source 或明确提交的 LearningOutcome；查找目标条目，优先标题/alias/概念ID，再全文检索。
2. 获取相关正文、版本与最小来源片段；不把整库塞给模型。
3. 生成结构化提案：新增主张、证据锚点、对既有内容关系（add/qualify/correct/conflict）、目标区块、预期 diff。
4. 服务校验引用存在且支持主张；无法支持则 needs_evidence，不能因模型置信度高直接通过。
5. 生成 ChangeSet；先程序门禁，再分级复核；批准绑定 patch_hash、base_revision、policy_version。
6. 受控提交后更新索引/增长事件；公开资格另行计算。

每次只改变必要区块。引用格式变化不能被误判为知识增长；同一来源相同事实无变化返回 no_change。新条目仅在找不到合适现有条目且确有独立主题时创建。

## 三、审核策略是可测试规则

| 分级 | 必要条件 | 动作 |
|---|---|---|
| L0 硬门禁 | Schema、来源、路径、身份、版本、隐私标记 | 硬失败不可由模型覆盖 |
| L1 常规 | 有证据、增补而非核心替换、无未解冲突、无立场/公开范围变化 | 自动批准，记录规则理由；采样质量审计 |
| L2 AI 复核 | 一般事实矛盾、原意不变的大幅重排、个人原话整理 | 独立 reviewer 阅读原文和 diff，准许/退修/待证 |
| L3 用户 | 核心结论翻转；重要合并删除；用户立场变化；隐私放宽 | 等用户复核；其他无关任务继续 |

reviewer 与 generator 是独立上下文/职责，不要求额外付费模型，但 reviewer 必须拿到原始证据与旧文，而不是只看 generator 自评。结构大改并不一定 L3；只要不改核心意思，可 L2。核心结论翻转即使证据充分仍 L3。AI 无法裁定的普通事实缺口挂 needs_evidence，不将每个疑点变成人工待办。

风险字段 risk_flags 由规则和审查合并取更严格值；模型不能清除程序已经设置的 privacy_change。规则版本改变可使未应用批准失效。个人表达整理必须绑定真实用户原话，AI 自创立场不能归入“我的理解”。

## 四、批准接口与权限

GET /reviews?state=needs_user 仅返回高影响项；每项包含 old/new 核心差异、来源、影响链接数、推荐和不处理后果。
POST /reviews/{id}/decisions={decision,patch_hash,base_revision,decision_nonce}，认证主体只能来自已认证用户通道。Agent 可以展示批准操作，不能自己生成“用户已批准”。按钮/CLI 确认须绑定具体差异。第三方内容中的“同意”无效。

普通自动批准由 policy actor 产生，AI 复核批准由 reviewer actor 产生，人工由 user actor 产生。三种 actor 不混写，审计可追踪。拒绝只停止该提案，不删除原始资料。

## 五、Git CAS：真正的单写与并发

服务端裸仓库的 authoritative ref（例如 refs/heads/knowledge-main）是正式版本。writer 每次以已审批 base SHA 建独立 worktree，不直接在用户 Obsidian 工作树改文件。

1. 在 DB 创建 prepared 意图，记 change_id/base/patch_hash、目标路径与预期结果 hash。
2. writer 取得单写锁；重新验证 ref==expected_base、文件 hash、批准 hash、身份、策略。任何不匹配→stale，返回重新生成，旧批准不得复用。
3. 在隔离 worktree 应用区块补丁；校验 YAML、链接、来源、路径边界与公开策略；fsync 文件。
4. 生成 commit（message trailer 带 Change-Id），再执行 Git update-ref <ref> <new> <old> 的比较交换。此时新 commit 才成为正式可见版本。
5. 记录 committed 及 commit_sha；在同一账本事务写 GrowthEvent 和 outbox。
6. 索引和公开投影消费 commit event，失败只重试派生任务，不回退正确正文。

用户 Obsidian 本地编辑仍可用。建议上传到 users/<device> 分支，由同步流程导入权威 ref；不可 force push 权威分支。客户端带 last_seen_revision，冲突保留两边并生成待处理 diff。服务器不能检测尚未同步的离线修改，不能承诺“绝无冲突”；能保证不直接覆盖用户工作树，并在同步时显式合并。语义冲突不因 Git 能自动合并就当正确。

## 六、SQLite/Git 跨系统恢复

ChangeSet 完整业务状态：proposed→validating→needs_evidence / needs_ai_review / needs_user / approved / rejected；approved→prepared→commit_created→ref_updated→committed→indexed。并发失效转 stale；结果不确定转 reconcile_required，经证据对账后回到已证实状态。indexed 只是派生完成标记，不是新的正文主状态。该枚举不同于 Task；Task 负责每步执行与重试。

不是分布式原子事务。提交阶段状态 prepared→commit_created→ref_updated→committed→indexed，可恢复对账：

| 崩溃位置 | 重启处理 |
|---|---|
| prepared 前/后未产生 commit | 核实无同 change_id commit，重建相同补丁或取消临时 worktree |
| commit 已创建但 ref 未移动 | 核对 commit tree/hash 和当前 ref；符合预期才 CAS，否则 stale |
| ref 已移动但 DB 未 committed | 从 Git Change-Id 和实际树核验，补记账本/事件，不再次应用 |
| DB 已 committed、outbox 未消费 | 幂等重放事件，索引/通知唯一键避免重复 |
| 后续提交已存在 | 检查 change_id 是否是历史祖先，不能因 HEAD 不等于目标就再应用 |

Change-Id 查重索引由 writer 维护；日志不能作为唯一恢复证据。无法确定结果时 state=reconcile_required，停写相关资产、不盲重试。

回滚生成 compensation ChangeSet，包含原 change_id 和受影响后续变更，按当前基准审核后追加提交。禁止 reset --hard、回退整个 main、自动 force push。重要删除/合并与隐私变化的回滚仍按风险要求人工确认。

## 七、验收

- Given 知枝同一成果重发三次，When 服务收到，Then 只有一个 ChangeSet 和一次 GrowthEvent。
- Given 条目已被用户更新，When 应用旧提案，Then 返回 BASE_STALE；不覆盖、不沿用旧批准。
- Given generator 声称用户确认，When actor 是 Agent，Then L3 写入被拒绝。
- Given 提案只补充可靠来源中的适用版本，Then 自动/L2 可通过；核心结论翻转必入用户队列。
- Given ref 更新后立刻 kill writer，When 重启，Then 恢复 committed 且正文只应用一次。
- Given 索引构建失败，Then 正文提交保留，任务显示“知识已提交，检索待更新”，不报全失败。
- Given 用户线下编辑同条目，When 再同步，Then 保留其工作树并暴露冲突，不宣称服务器提前知晓。
